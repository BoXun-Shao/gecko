# 需求書：資料庫化與商用架構規劃

- **訪談日期**：2026-08-23
- **範圍/主題**：把資料儲存從瀏覽器 `localStorage` 改為自建後端 API + 資料庫，並以「未來可能商用（多使用者）」的角度規劃架構，即使目前功能上仍只服務使用者本人。

## 背景

專案原本是單一 HTML 檔、無建置流程、無後端的個人工具，資料存在瀏覽器 `localStorage`。使用者現在要求：即使目前只有自己用，也要用「未來可能商用」的角度規劃資料庫與架構，避免之後要大改。這是**專案性質層級的重大變更**，會讓 [CLAUDE.md](../../CLAUDE.md) 中「單一 HTML 檔、無建置流程、無後端」的專案性質描述失效，需要同步更新。

## 架構決策

| 項目 | 決策 | 備註 |
|---|---|---|
| 後端 | 自建 API，Python（FastAPI） | 不採用 Supabase 等 BaaS，選擇自己掌控後端邏輯 |
| 資料庫 | PostgreSQL | 與原 Roadmap 方向一致 |
| 前端 | React | 取代現有 vanilla JS + 單一 HTML 檔架構 |
| 建置工具 | 需要（例如 Vite），細節留給實作階段決定 | 因改用 React，「無建置流程」的限制不再成立 |
| 部署目標 | 尚未決定，這次先以本機開發/測試為目標 | 部署方案（雲端 PaaS／自有 VPS）留待後續需求訪談 |

## 多使用者與認證設計方向

- **這次不實作登入 UI**，但資料庫 schema 要先往「未來支援多使用者」的方向設計，避免之後加登入要大改 schema。
- 認證方式方向：**Email + 密碼（自建認證）**。`user` 表與密碼雜湊欄位等結構這次就先建立。
- **本次 API 身份識別方式**：Seed 一筆固定的預設 `user`，所有資料表都帶 `user_id` 外鍵並實際指向這筆預設 user；所有 API 呼叫（沒有登入機制）都對應到這筆 user。未來加上真正的登入驗證時，只需要替換「怎麼決定 user_id」這一段邏輯，資料庫 schema 與 API 形狀不需要改變。

## 資料儲存

- **照片/檔案**：存在**後端伺服器本地檔案系統**（非物件儲存服務如 S3），資料庫只存路徑。
  - 這與 [2026-08-23-紀錄功能重新規劃.md](2026-08-23-紀錄功能重新規劃.md) 中「蛻皮紀錄可上傳多張照片」的需求相關；改用後端檔案系統儲存後，原本針對 `localStorage` 容量的疑慮不再適用，但要注意伺服器磁碟空間與備份策略（後續視實際使用量再議，非本次需求範圍）。
- **紀錄資料表結構**：須涵蓋 [2026-08-23-紀錄功能重新規劃.md](2026-08-23-紀錄功能重新規劃.md) 中定義的守宮基本資料、進食（含新 `status` 列舉：`fed`/`partial`/`refused`/`skipped`）、排便、體重、蛻皮、環境溫濕度（含每隻可各自設定的安全範圍）——資料庫 schema 設計時必須與該需求書的欄位定義保持一致，不可重新發明欄位。

## 資料遷移（localStorage → PostgreSQL）

- 流程：使用者先用現有「匯出 Excel」功能，把 `localStorage` 資料匯出成 Excel 檔 → 撰寫**一次性匯入工具**讀取該 Excel 檔 → 寫入 PostgreSQL。
- 此匯入工具是一次性的（onboarding 用），不是常態雙向同步機制。

## Excel 匯出/匯入功能

- **保留**，在新架構下轉型為「備份/匯出」功能，而非唯一資料來源。DB 才是主要且可靠的儲存位置。

## 舊版（單一 HTML 檔）處理

- 新版（React + FastAPI + PostgreSQL）功能與現有 `index.html` **對等**之後，**直接淘汰/移除**舊版，不長期並存、不保留離線備援版本。
- 「功能對等」的判斷基準：新版須完整涵蓋 README 現有功能清單 + [2026-08-23-紀錄功能重新規劃.md](2026-08-23-紀錄功能重新規劃.md) 定義的新紀錄類型。

## 建議分期（工程判斷，非需求訪談決議，執行順序如需調整可再討論）

1. 後端專案骨架：FastAPI + PostgreSQL 連線、user/gecko/log 資料表 migration、seed 預設 user
2. API endpoints：涵蓋現有功能 + 2026-08-23 紀錄功能重新規劃的所有欄位（進食 status、蛻皮、溫濕度）
3. 前端重寫：React 專案，呼叫新 API，取代 localStorage 操作邏輯
4. 一次性資料遷移工具：Excel → PostgreSQL
5. Excel 匯出/匯入功能在新架構下的實作
6. 功能對等驗證 → 淘汰舊版 `index.html`
