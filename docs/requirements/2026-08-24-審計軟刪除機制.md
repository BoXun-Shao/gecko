# 需求書：全表 created_at/updated_at/is_deleted + Audit Log 機制

- **訪談日期**：2026-08-24
- **範圍/主題**：擴充 [2026-08-24-資料庫schema定案.md](2026-08-24-資料庫schema定案.md) 定案的 7 張業務資料表，統一補上時間戳與軟刪除欄位，並新增全域 audit log 機制記錄所有資料異動。

## 背景

使用者要求「每張表都要有 created_at、updated_at、is_deleted」以及「任何一筆資料庫的新增/修改，都要有 audit log 紀錄」。

這與已定案的 [2026-08-24-資料庫schema定案.md](2026-08-24-資料庫schema定案.md) 有衝突/未涵蓋之處：
- `shedding_photos`、`environment_logs` 原本完全沒有 `created_at`/`updated_at`。
- 其餘表雖有 `created_at`，但都沒有 `updated_at`。
- 完全沒有軟刪除（`is_deleted`）機制，`users.email` 與 `daily_logs (gecko_id, date)` 的 UNIQUE 限制都是針對「全部資料」而非「未刪除資料」。
- 完全沒有 audit log 表或機制。

依專案 CLAUDE.md 的「需求驅動開發」規則，動工前先訪談確認以下開放性問題。

## 需求細項（已確認）

### 1. 每張業務資料表統一新增欄位
- `created_at`：timestamptz，not null，`server_default=now()`
- `updated_at`：timestamptz，not null，`server_default=now()`，ORM 層 `onupdate=func.now()`
- `is_deleted`：boolean，not null，預設 `false`
- `deleted_at`：timestamptz，nullable（刪除當下寫入時間）

套用範圍：`users`、`geckos`、`daily_logs`、`shedding_logs`、`shedding_photos`、`environment_logs`、`egg_logs`（原 [schema 定案書](2026-08-24-資料庫schema定案.md) 的全部 7 張業務表）。

**例外：`audit_logs` 本身不套用這組欄位。** 它是附加式（append-only）的稽核紀錄表：稽核紀錄不會被刪除，也不需要「對稽核紀錄本身的異動再產生稽核紀錄」，否則會遞迴。這點在訪談中提出並由使用者默認採用（見下方實作備註）。

### 2. Audit log 機制
| 決策點 | 選項 | 決定 |
|---|---|---|
| 寫入機制 | SQLAlchemy ORM event listener vs. PostgreSQL trigger | **ORM event listener**（`before_flush`）。理由：目前資料庫唯一的寫入路徑是透過本專案的 SQLAlchemy session（尚無任何其他服務或手動 SQL 寫入路徑），純 Python 實作較好維護、除錯直覺。若未來出現繞過 ORM 的寫入路徑，需重新評估是否改用/加上 DB trigger。 |
| 記錄粒度 | 只記變動欄位（diff） vs. 整列 snapshot | **只記變動的欄位（diff）**。`update` 只包含真的變動的欄位；`insert`/`delete`（硬刪除）因為沒有「舊值」或「新值」可比較，記錄為該筆的全部欄位（insert 全部 old=null，delete 全部 new=null）。 |

### 3. audit_logs 資料表結構
| 欄位 | 型別 | 說明 |
|---|---|---|
| id | UUID (PK) | |
| table_name | text | 被異動的表名 |
| record_id | UUID | 被異動那筆資料的 PK |
| action | enum('insert','update','delete') | |
| diff | JSONB | `{欄位: {"old": ..., "new": ...}}`，只含異動欄位（見上） |
| changed_by | UUID (FK → users, nullable) | 誰做的異動；目前系統尚無登入 UI，實務上會是 null 或固定 seed user，待未來接上登入機制後由 API 層帶入 |
| changed_at | timestamptz | `server_default=now()` |

### 4. 軟刪除與既有 UNIQUE 限制的衝突
| 決策點 | 選項 | 決定 |
|---|---|---|
| `daily_logs` 的 `UNIQUE(gecko_id, date)` | 維持限制全部資料 vs. 改成只限制未刪除資料 | **改成 partial unique index**：`UNIQUE(gecko_id, date) WHERE is_deleted = false`。允許使用者刪除某天紀錄後，同一天重新補登。 |
| `users.email` 的 UNIQUE | 同上邏輯是否套用 | **比照套用**，改成 `UNIQUE(email) WHERE is_deleted = false`。原需求書只問到 `daily_logs`，但兩者是同一類問題（軟刪除的資料是否仍佔用唯一值），故延伸套用同一決策，避免同一原則在不同表出現不一致行為。 |

## 實作備註（非需求，供對照程式碼用）

- 共用欄位透過 `TimestampMixin`（`backend/app/models.py`）以 mixin 方式套用到 7 張業務表，避免重複定義。
- Audit event listener 實作於 `backend/app/audit.py`，透過 `app/__init__.py` 匯入以確保註冊。
- 已知限制：目前系統尚無 CRUD delete API，「父表軟刪除時子表如何處理」（現有 `cascade="all, delete-orphan"` 是硬刪除子表，跟軟刪除語意不一致）**本輪不處理**，待實際開發刪除功能的 API 時再訪談確認 cascade 軟刪除的行為。
- Migration：`backend/alembic/versions/80e4a2510daf_*.py`。
- Schema 文件：`docs/database/schema.md`，透過 `backend/scripts/generate_schema_doc.py` 自動產生。
