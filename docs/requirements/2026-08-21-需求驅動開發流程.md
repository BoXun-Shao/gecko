# 需求書：需求驅動開發流程

- **訪談日期**：2026-08-21
- **範圍/主題**：定義開發流程中「需求書」的角色，以及實作選擇與需求書衝突時的處理方式。

## 背景

在建立 SDLC 流程規範（見 [2026-08-21-建立SDLC流程規範.md](2026-08-21-建立SDLC流程規範.md)）之後，使用者進一步要求：開發必須先有需求書、依需求書開發，且實作中若與需求書衝突要立即提出並重新訪談確認。

## 需求細項與決策

| 主題 | 決策 | 理由/備註 |
|---|---|---|
| 需求書存放方式 | `docs/requirements/`，每次新需求訪談完成後建立一份新文件，命名 `YYYY-MM-DD-主題.md` | 保留每次訪談的完整歷史記錄，不覆蓋舊文件 |
| 需求書 vs TODO.md 的關係 | 需求書是 source of truth，TODO.md 只是從需求書萃取的待辦追蹤（勾選狀態用） | 避免兩份文件互相打架，細節永遠回頭查需求書 |
| 開發前置條件 | 沒有需求書涵蓋的工作不開發，訪談沒問清楚的地方不邊做邊猜 | 避免「合理猜測」造成後續返工 |
| 實作與需求書衝突時的處理 | 立即停止該項工作 → 向用戶說明衝突點 → 重新進行需求訪談確認 → 更新/新增需求書 → 才能繼續 | 使用者明確要求「立即停下來，馬上詢問」，不要先斬後奏或先記錄晚點問 |
| 需求異動記錄方式 | 一律新增新需求書記錄異動，不覆蓋舊需求書 | 保留完整決策歷史，呼應上一份需求書「保留歷史」的精神 |
