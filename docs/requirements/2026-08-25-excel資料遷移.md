# 需求書：舊版 Excel 匯出檔 → PostgreSQL 一次性資料遷移

- **訪談日期**：2026-08-25
- **範圍/主題**：實作 [TODO.md](../../TODO.md) 中「一次性資料遷移工具：讀現有 Excel 匯出檔 → 寫入 PostgreSQL」，把使用者從舊版 `index.html` 匯出的 Excel 檔匯入新的後端資料庫。

## 背景

使用者已經有一份從 `index.html` 匯出的 Excel 檔案，要匯入現在的 PostgreSQL 資料庫。TODO.md 只有一行描述，沒有實作細節，依 CLAUDE.md 規則先確認開放性問題再動工。

現況（讀 [index.html](../../index.html) 匯出/匯入邏輯確認）：
- 匯出檔固定兩個工作表：「守宮」（欄位：ID／名字／品系／性別／出生日期／入手日期／餵食頻率(天)／備註／照片(請勿編輯)）與「餵食紀錄」（欄位：守宮ID／守宮名字／日期／餌料／尺寸／進食數量／狀態／排便／體重(g)／備註）。
- 目前 `index.html` 尚未實作蛻皮、環境溫濕度、下蛋紀錄（見 TODO.md 未勾選項目），所以舊版匯出檔不會有這些資料，這次遷移只處理守宮基本資料與每日進食/排便/體重紀錄。
- 「狀態」欄位是匯出時就已經算好的文字（進食/沒餵/拒食），不是原始的 `qty`/`skipped` 布林值。
- 「性別」欄位值域是「公」／「母」／空白（對應舊 UI 下拉選單）。
- 「照片(請勿編輯)」欄位是 base64 data URI（`data:image/png;base64,...`），不是檔案。
- 舊版 `uid()`（`Date.now().toString(36) + 亂數`）產生的 ID 不是合法 UUID，無法沿用當新資料庫的主鍵。

## 需求細項（已確認）

| 決策點 | 選項 | 決定 |
|---|---|---|
| 照片如何處理 | 解碼寫檔 vs. 這輪先不處理 | **解碼寫檔**到 `backend/uploads/geckos/<gecko_id>.<ext>`，`photo_path` 存相對路徑（`uploads/geckos/...`）。理由：這也順便訂出以後上傳 API 要沿用的目錄慣例。`backend/uploads/` 已加進 `.gitignore`（使用者資料不進版控）。 |
| `沒餵`／`拒食` 的 `qty` 怎麼寫 | 都存 0 / 都存 null / 分開處理 | **分開處理**：`拒食`（有餵、吃 0 個）→ `qty=0`，是有意義的資訊；`沒餵`（非餵食日）→ `qty=null`，因為當天根本不適用「吃了幾個」這個問題。`進食` → `qty` 用 Excel 原始數字。不會產生 `partial`（沿用 [2026-08-23-紀錄功能重新規劃.md](2026-08-23-紀錄功能重新規劃.md) 既有決策：舊資料沒有部分進食的判斷依據）。 |
| 重複執行怎麼避免重複資料 | Upsert vs. 假設乾淨資料庫 | **Upsert**。守宮用「名字」比對（無法用 ID，見上述 `uid()` 不是 UUID 的問題）；每日紀錄用 `(gecko_id, date)` 比對，對應 `daily_logs` 的 partial unique index。腳本可以放心重複執行，不會產生重複資料；照片檔名用資料庫的 gecko UUID（穩定），重跑會覆蓋同一個檔案而不是產生新檔案。 |
| 所有資料要掛在哪個 user 底下 | — | 掛在 `DEFAULT_USER_ID`（目前系統唯一的固定 seed user）。系統還沒有登入 UI，這是既有的既定假設，不是本次新決策。 |

## 實作備註（非需求，供對照程式碼用）

- 腳本：[backend/scripts/migrate_excel.py](../../backend/scripts/migrate_excel.py)，用法：`python -m scripts.migrate_excel <xlsx 路徑>`（於 `backend/` 目錄下執行）。
- 新增依賴：`openpyxl`（讀取 .xlsx；舊專案沒有 pandas，選擇最輕量的讀取方式）。
- 因為腳本透過 SQLAlchemy ORM 寫入，[audit_logs](2026-08-24-審計軟刪除機制.md) 會自動記錄這次遷移寫入的每一筆 insert/update，不需要額外處理。
- 已用合成的測試 Excel 檔（模擬真實匯出格式，含一張 1x1 PNG 測試照片）驗證過：新增/更新計數正確、性別對應正確、狀態/`qty` 規則正確、照片有解碼寫檔、重複執行會 upsert 而非產生重複資料。測試資料已清除，不影響正式資料庫。
